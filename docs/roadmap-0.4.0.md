# 0.4.0 開発計画（2026-11-01）

基準は公開済みの **v0.3.0**（タグ `794a994`）です。次版を0.4.0候補として開発を始めます。
この文書は計画であり、対応機能・公開日を約束するものではありません。
版番号・依存バージョンは公開範囲が固まるまで0.3.0のままにします。

## 第三者レビューの扱い

レビューの「UIへの責任集中」「性能の実測不足」「失敗時の検証不足」を改善候補に採用します。
ただし、コードを直接確認して再現・計測した問題と、懸念・推測を区別します。
「毎フレーム再構築」「メモリリーク」「実行検証の抜け穴」はレビューだけでは確定しません。
他ツールの保守状況や優劣も未検証なので、紹介記事やマニュアルの比較表へ転記しません。

レビュー前半の「公開版0.2.0／0.3.0開発中」は現在と異なります。
公開記録は[0.3.0リリース記録](release-0.3.0.md)、利用者向けの基準は0.3.0マニュアルです。
古い[0.3.0計画](roadmap-0.3.0.md)は当時の履歴として残します。

## 実装の優先順序

1. **結果表示の性能を測り、確認できた無駄を減らす。**
   プローブ、コンター再構築、読み込み、選択を別々に計測する。
   静止時・ホバー・フレーム変更・変形倍率変更で何が再構築されるかを回帰テストで確認する。
   測定環境・メッシュ規模・形式・ビルド種別・計測範囲を記録し、未測定の上限を宣伝しない。
2. **UIの責務を小さく分け、操作を通したテストを追加する。**
   まず結果プローブのキャッシュを表示から切り離す。
   次に結果読込・Solve実行などの状態遷移と表示の境界を点検する。
   機械的な大移動や公開クレート追加を先行させず、数値・選択・Undo等の既存仕様を守る。
3. **ソルバー失敗・中止・再実行の復帰を検証する。**
   分割失敗でソルバーが始まらないこと、Stop後の子プロセス・ログ・実行ボタンの状態、
   古い結果の誤読込防止を小さなプロセスfixtureで再現し、不足分を補う。
   実機MPI確認とfixture成功を区別する。例題・元入力を破壊するクリーンアップは行わない。
4. **解析設定の対応範囲を、利用者が判断できる形で整理する。**
   GROUP／ACTIONの単体保持と、複数部品統合時の参照制限を明記する。
   名前付き出力GROUPの参照変換は候補として、公式仕様・現コード・往復テストを照合して採否を決める。
   未対応カードを黙って捨てないガードを維持する。
5. **操作感・情報密度を改善する。**
   リリース後へ持ち越したSolidCraft風カメラ操作を再検討する。
   既存操作の保存、選択／姿勢編集との干渉、回転中心・極付近の挙動を検証する。
   HISTORY／COMPARISONの折りたたみは、警告と保存対象を隠さず状態を維持できる場合に検討する。
6. **公開範囲の確定と検証・配布。**
   Windows／Linux CI、設定保存・再読込、結果／CSV、配布物、監査、マニュアルを確認する。
   機能の区切りでcommitし、公開時にmainへ統合、版番号・内部依存・タグ・crates.io・Windows ZIPを揃える。
   コミット・push・タグはメンテナーが行う。公開済みv0.3.0は変更しない。

## 最初の区切り: プローブのキャッシュと計測

作業ブランチ: `perf/result-probe-cache`（main `cb4c1b2`から開始）。

- 確認した問題: `VisualizationSettings`全体の変更フラグでプローブのBVHを破棄していたため、
  Wire等の描画モード変更や同じ値の代入後にも、次のホバーで再構築していた。
- 改善: 結果・モデル更新は引き続き破棄対象とし、コンター設定は値を比較する。
  再生／UI操作中も無効化を記録し、次に必要になったときだけ構築する。
- テスト: 表示モード・同値代入で再利用、再生中のフレーム変更後に正しい値を取得、
  変形・物理量・モデル差替え・欠損フィールドで古い幾何を使わないこと。
- CPU計測: 合成Hex8格子の準備、変形面BVH構築、キャッシュ済み4096レイの照会を分離する。
  [計測手順](performance.md)に従い、描画FPSや大規模実モデルの保証と混同しない。

検証（2026-11-01）: UI 214件・可視化33件成功、失敗0、実機MPI依存1件スキップ。
`cargo +1.99.1 test -p bevyistr-ui -p bevyistr-visualization --lib --locked --offline`を使用。
Release計測例は729～274,625節点の4規模で全4096レイの値・距離を確認した。
mdBookビルド、変更したRustファイルの整形検査、diff空白検査に成功。
TEMP／TMPとリンクのPDB無効化は検証プロセス内だけに指定した。
GUI実機操作とLinux実行、実データの速度・メモリは今回未確認。

## 結果読込とUI状態管理の分離（2026-11-01）

`30a3928`のcommit／pushとクリーンな作業ツリーを確認して継続。
手動のOpen Resultsについて、VTK／RES／既存FRDのファイル処理とバックグラウンド読込を
`ui/src/result_loading.rs`へ分離しました。ダイアログ、ページ、コンター、シーク、カメラの更新は
`result_open.rs`側に残します。UI操作を行わずに読み込みを検証できる境界を作る変更です。
公開クレート・外部API・依存関係は増やしません。

- 読込入力をVTK／メッシュ付き結果の型で区別し、ワーカー内でメッシュ入力をunwrapする経路を除去。
- 空の結果、形状と区画数の不整合、区画間のフレーム数不整合、表示フィールドのないフレームを
  画面へ適用する前に拒否する。既存ローダーの座標／ID／フィールド等の検査は維持。
- ワーカー開始失敗・通信切断・空結果を通常の失敗として表示し、古い表示を保持する。
  空の結果で`Loading...`が残る経路を修正。
- 検証: 一時ファイルからのVTK単独読込、MSHファイル／現在メッシュを使うRES読込、
  飛び番Stepと節点ID順、後続ファイルの失敗、待機／完了／切断、受信側破棄後の遅延結果。
  受信側破棄は結果を適用しないという検証であり、バックグラウンド処理の強制停止ではない。
- ECS回帰: 待機後に空結果・エラー・切断が起きても、プリ形状・結果形状・数値・コンター・ページ・
  シーク・再生状態・カメラ要求を維持し、待機表示を終了することを確認。
- 既存の正常読込／Modelとの往復、フィールド選択からファイルダイアログが開かない回帰も成功。

検証: `cargo +1.99.1 test -p bevyistr-ui --lib --locked --offline`で220件成功、失敗0、
実機MPI依存1件をスキップ。TEMP／TMP・PDB無効化は検証プロセス内のみ。

## 手動／自動結果読込の競合防止（2026-11-01）

`3abd4a1`のcommit／pushとクリーンな作業ツリーを確認して継続。
手動読込は自動読込の待ちを取り消していた一方、逆方向の制御がなく、古い手動結果が後から
表示を上書きする余地があった。自動結果を表示しても手動ファイル名の案内が残る経路も確認した。

- 両方の経路で要求の順序を共有し、最後に受け付けた要求だけを適用する。
  古い成功・エラーは、受信済みでも遅延到着でも画面へ適用しない。
- 手動選択のキャンセルや手動ワーカー開始失敗では新しい要求を発行しない。
  新しい要求が失敗した場合は直前の表示を維持し、古い待ち結果を代わりに表示しない。
- 同一フレームでは、自動要求の処理後に手動の受付を行う。結果の反映をスライダー・統計表示より前に、
  結果形状の表示切替を両方の反映後にそろえる。モデル版／実行IDの既存検査は維持。
- 古い手動読込の待ちと出典案内を解除し、自動表示に以前の手動ファイル名を残さない。
- 手動結果の独立形状から解析対象モデルへ戻る場合は、切替先へカメラを合わせる。
  新しい要求が失敗した場合や古い完了を破棄する場合は、この切替を行わない。
- 制御した通信fixtureで、両方向・反映処理の実行順・受信済み／遅延・新旧の失敗を確認する。
  実機GUIや実際の長時間解析を再実行する代わりの保証にはしない。

取り消しは受信結果の不適用であり、バックグラウンド処理の強制停止ではない。
公開済み0.3.0・版番号・タグ・公開物は変更しない。

検証: `cargo +1.99.1 test -p bevyistr-ui --lib --locked --offline`で224件成功、失敗0、
実機MPI依存1件をスキップ。UI全体のスケジュール組立の回帰も成功。
mdBookビルド・diff空白検査も成功。GUI実機・実MPI・Linux実行は今回未確認。

## ソルバー通信切断時の復帰（2026-11-01）

`df93f69`のcommit／pushとクリーンな作業ツリーを確認して継続。
分割失敗・Stop・古い分割ファイルの再利用防止には既存テストがある一方、
ワーカーが完了通知を送らずに通信を閉じると、画面がRunningに残り再実行できない経路を確認した。

- 通信の待機と切断を区別し、未処理のログを取り込んだ後で失敗を一度だけ通知する。
  1回のポーリングで処理するイベントは従来どおり最大256件とする。
- 通常の成功・非ゼロ終了・Stop・起動失敗の通知がある場合は、その結果を維持する。
  通知と切断が別のポーリングに分かれても、切断を追加の失敗として報告しない。
- 既存の失敗処理を通して実行中状態・Stop待ちを解除し、失敗した結果は自動表示しない。
  同じ出力先で次の入力準備ができることを確認する。
- 追加3テストでは、600行のログの順序と分割取得、終端通知の保持、
  RunningからFailedへの復帰とReadyへの再準備を制御した通信fixtureで検証する。

実際のFrontISTR／MPIの異常終了や再実行成功を再現した検証ではない。
流体例題は保留を維持し、版番号・公開済み0.3.0・公開物は変更しない。

検証: `cargo +1.99.1 test -p bevyistr-ui --lib --locked --offline`で227件成功、失敗0、
実機MPI依存1件をスキップ。分割失敗・Stop・再分割時の古い出力の拒否を含む既存fixtureも成功。
